# Requirements Document

## Introduction

This document covers Phase 0 (Base) of the programming tutor (`tutor-agent`). Phase 0 delivers the visible foundation: a Vite + React front end with three zones (lesson, editor with results, chat), a TypeScript API that implements the full contract with fixed (mock) responses, the `shared/` package with the contract, the sample module 3, and the minimal CDK infrastructure (S3 + CloudFront, and API Gateway REST + Lambdas).

Phase scope:
- The whole API contract (`/api/modules`, `/api/modules/{id}/lesson`, `/api/exercises/{id}`, `/api/chat`, `/api/hint`, `/api/run`, `/api/progress`) answers with fixed data.
- There is no agent, no Bedrock, no AgentCore, no real code execution, no memory and no login. Those extension points stay in the contract for Phases 1 to 5.
- The Python project with uv (`agent/`) is created in Phase 1.

Exit criterion: the student opens the CloudFront URL, reads the lesson of module 3, writes code, presses "Ejecutar", asks for hints and sees the simulated tutor reply arrive by streaming. The phase ends with the `fase-0` git tag and the draft of Post 1.

Language convention: code, comments and this spec are in English. Text shown to the student (UI and tutor) is in Spanish.

## Glossary

- **Contract**: zod schemas and TypeScript types in `shared/`, the source of truth of the API.
- **Mock**: a fixed response produced by the API without an agent and without code execution.
- **Session**: the `sessionId` generated by the front end and used to correlate logs.
- **Hint**: help at level 1 (orientation), 2 (structure) or 3 (almost the solution).

## Requirements

### Requirement 1: Repository, structure and roadmap

**User Story:** As the project developer, I want a repository with the agreed structure and a README with the roadmap, so that each phase adds code without restructuring.

#### Acceptance Criteria

1. THE repository SHALL contain the directories `shared/`, `web/`, `api/`, `infra/`, `content/`, `scripts/` and `docs/posts/` as defined in `structure.md`.
2. THE repository SHALL use a single root `package.json` with npm workspaces for `shared`, `web`, `api` and `infra`, and a single committed `package-lock.json`.
3. THE README SHALL describe the roadmap of Phases 0 to 5, the install, test, `cdk synth` and `cdk deploy` commands, and how to run the front end and the API locally.
4. THE repository SHALL NOT contain the `agent/` directory in this phase.
5. WHEN the phase is closed, THEN the repository SHALL carry the git tag `fase-0`.

### Requirement 2: `shared/` package with the API contract

**User Story:** As a developer, I want a single source of truth for the contract, so that the front end and the API never drift apart.

#### Acceptance Criteria

1. THE `shared/` package SHALL export zod schemas and inferred types for `Module`, `Lesson`, `Exercise`, `ChatRequest`, `ChatStreamEvent` (`token`, `done`, `error`), `HintRequest`, `HintResponse`, `RunRequest`, `RunResult`, `Progress` and `ApiError`.
2. THE types `Module`, `Exercise`, `ChatRequest`, `HintRequest`, `RunRequest`, `RunResult` and `Progress` SHALL match section 6 of `stacky.md`.
3. THE `web/` and `api/` packages SHALL import types and schemas from `shared/` and SHALL NOT redefine them.
4. THE public `Exercise` schema SHALL NOT include the fields `solution`, `hints` or `tests`.
5. THE `ChatRequest` schema SHALL require non-empty `sessionId`, `exerciseId` and `message`, and SHALL limit `message` to 2000 characters.
6. IF OpenAPI documentation is needed, THEN it SHALL be handled as open decision 6 of `stacky.md` and SHALL NOT be generated in this phase.
7. THE `shared/` package SHALL export a helper `exerciseIdsFor(module)` that derives the exercise ids of a module from its id and `exerciseCount` using the `mNN-eMM` convention (for example `modulo-03-condicionales` with count 3 gives `m03-e01`, `m03-e02`, `m03-e03`), because the contract has no endpoint that lists the exercises of a module.
8. THE front end SHALL use `exerciseIdsFor` to discover the exercises of a module, and a content test SHALL fail when the content does not follow the convention.

### Requirement 3: Three-zone layout

**User Story:** As a student, I want to see the lesson, the editor with results and the chat on one screen, so that I can study without switching pages.

#### Acceptance Criteria

1. THE application SHALL show a `Header` and three zones: `LessonPanel`, `EditorPanel` with `ResultsPanel`, and `TutorChat`.
2. WHILE the screen width is below 900 px, THE application SHALL stack the zones in a single column without losing functionality.
3. THE interface text SHALL be in Spanish and the code and comments SHALL be in English.
4. WHEN the application loads, THEN it SHALL select by default the first module and the first exercise returned by the API.
5. WHILE the initial data is loading, THE application SHALL show an accessible loading state.
6. IF the initial load fails, THEN THE application SHALL show an error message in Spanish with a "Reintentar" button.

### Requirement 4: Lesson and exercise

**User Story:** As a student, I want to read the lesson and the exercise statement, so that I know what to program.

#### Acceptance Criteria

1. WHEN a module is selected, THEN `LessonPanel` SHALL show the lesson Markdown rendered with `react-markdown`.
2. THE `LessonPanel` SHALL NOT render raw HTML contained in the Markdown.
3. WHEN an exercise is selected, THEN THE application SHALL show its title, statement and difficulty.
4. THE application SHALL let the student switch between the 3 exercises of module 3.
5. WHEN the exercise changes, THEN THE editor SHALL load the `starterCode` of the new exercise.

### Requirement 5: Editor and simulated execution

**User Story:** As a student, I want to write code and press "Ejecutar" to see test results, so that I can practice the write-and-test cycle.

#### Acceptance Criteria

1. THE `EditorPanel` SHALL use `@monaco-editor/react` with Python syntax highlighting.
2. WHEN the student presses "Ejecutar", THEN THE front end SHALL send `POST /api/run` with `exerciseId` and `code` through `src/api/client.ts`.
3. WHILE a run is in progress, THE "Ejecutar" button SHALL be disabled and SHALL show a progress indicator.
4. WHEN a `RunResult` arrives, THEN `ResultsPanel` SHALL show each test with its name, passed or failed status and message, plus `stdout` and `stderr`.
5. IF the submitted code is identical to the `starterCode`, THEN THE `/api/run` mock SHALL return every test as failed with the message "Ejecución simulada (Fase 0)".
6. IF the submitted code differs from the `starterCode`, THEN THE mock SHALL return every test as passed.
7. THE API SHALL NOT execute, evaluate or interpret the received code under any circumstances.
8. WHEN `RunResult.passed` is true, THEN THE interface SHALL show a short celebration message and mark the exercise as completed in the front-end local state only.

### Requirement 6: Simulated tutor chat with SSE streaming

**User Story:** As a student, I want to talk to the tutor and see its reply appear gradually, so that the conversation feels natural.

#### Acceptance Criteria

1. WHEN the student sends a message, THEN THE front end SHALL call `POST /api/chat` through `client.ts` and process the SSE stream with the events `token`, `done` and `error`.
2. WHEN a `token` event arrives, THEN `TutorChat` SHALL append the text to the tutor message without waiting for the end of the stream.
3. WHEN the `done` event arrives, THEN `TutorChat` SHALL enable the input field again.
4. WHEN an `error` event arrives or the connection fails, THEN `TutorChat` SHALL show an error message in Spanish and allow retrying.
5. WHILE the tutor is replying, THE sending of new messages SHALL be disabled and the student SHALL be able to cancel the reply.
6. THE API in mock mode SHALL reply with a fixed Socratic-style text in Spanish, emitted in fragments with a short pause between `token` events.
7. THE mock SHALL emit the first `token` in under 1 second after receiving the request.
8. IF the body of `/api/chat` does not satisfy `ChatRequest`, THEN THE API SHALL respond 400 with a JSON `ApiError` and SHALL NOT open an SSE stream.
9. IF the mock simulates a failure during the stream, THEN THE API SHALL emit `event: error` with `{"message": "..."}` and close the stream.

### Requirement 7: Progressive hints

**User Story:** As a student, I want to ask for hints in three levels, so that I get gradual help without being given the answer.

#### Acceptance Criteria

1. THE interface SHALL offer three hint buttons, one per level.
2. WHILE level N-1 has not been used, THE button for level N SHALL be disabled.
3. WHEN the student asks for a hint, THEN THE front end SHALL send `POST /api/hint` with `exerciseId` and `level`.
4. THE API SHALL return `{ level, text }` with the hint text of that level defined in `ejercicios.json`.
5. IF `level` is not 1, 2 or 3, or `exerciseId` does not exist, THEN THE API SHALL respond 400 or 404 with an `ApiError`.
6. THE API SHALL NOT return the `solution` field in the `/api/hint` response.
7. WHERE the server controls hint progress in later phases, THE contract SHALL allow it without front-end changes (extension point; not implemented in this phase).

### Requirement 8: Single HTTP client

**User Story:** As a developer, I want a single HTTP exit point in the front end, so that I can change the backend without touching components.

#### Acceptance Criteria

1. EVERY HTTP and SSE call of the front end SHALL go through `web/src/api/client.ts`.
2. NO component or hook SHALL use `fetch` directly.
3. THE client SHALL read the base URL from `import.meta.env.VITE_API_URL`, and IF it is empty, THEN it SHALL use relative paths (`/api/...`).
4. THE client SHALL validate responses with the `shared/` schemas and throw a typed error when they do not match.
5. THE client SHALL send the `X-Session-Id` header with an identifier generated once per tab and stored in `sessionStorage`.
6. THE client SHALL process the SSE stream with `fetch` and `ReadableStream` (because the request is a POST), with cancellation support through `AbortController`.
7. THE client SHALL NOT contain credentials or secrets.

### Requirement 9: API with mock responses and validation

**User Story:** As a developer, I want the API to satisfy the full contract with fixed data, so that the front end does not change when the real agent arrives.

#### Acceptance Criteria

1. THE API SHALL implement the seven endpoints of section 6 of `stacky.md` with the exact routes, methods and shapes of the contract.
2. THE handlers SHALL validate input (body, path parameters and headers) with zod and the `shared/` schemas.
3. IF the input is invalid, THEN THE API SHALL respond 400 with an `ApiError` (`code`, `message`) without exposing internal traces.
4. IF the resource does not exist (module or exercise), THEN THE API SHALL respond 404 with an `ApiError`.
5. NO API response SHALL contain the `solution` field or its content.
6. THE API SHALL use one handler per responsibility: `content` (modules, lesson, exercise), `chat`, `hint`, `run` and `progress`. THE `chat` and `hint` handlers belong to the same tutor responsibility but SHALL be separate Lambda functions, because API Gateway does not support a streamified function behind a buffered integration.
7. THE API SHALL write structured JSON logs with `sessionId` (from `X-Session-Id` or from the body), route, method, status code and latency on every request.
8. `GET /api/progress` SHALL return a fixed `Progress` with an empty `completedExerciseIds` and `totalExercises` equal to the number of available exercises.
9. THE Lambdas SHALL be written in strict TypeScript and run on Node.js 22.x on arm64.

### Requirement 10: Module 3 content

**User Story:** As a student, I want a complete conditionals module, so that I can practice with real exercises.

#### Acceptance Criteria

1. THE directory `content/modulo-03-condicionales/` SHALL contain `leccion.md`, `ejercicios.json` and `errores-comunes.md`.
2. THE `leccion.md` file SHALL explain `if/elif/else` and booleans in Spanish, with analogies and small examples.
3. THE `ejercicios.json` file SHALL contain 3 exercises (`m03-e01`, `m03-e02`, `m03-e03`) of increasing difficulty that satisfy the schema in `structure.md`.
4. EACH exercise SHALL include 3 hints, at least 3 tests and a `solution`.
5. THE `ejercicios.json` schema SHALL be validated with a zod schema in `shared/` and a test that fails when the content is invalid.
6. THE `solution` SHALL exist only in `content/` and in server-side data, and SHALL NOT be copied to `web/`.
7. `GET /api/modules` SHALL return only the modules that have content available (in this phase, only module 3).

### Requirement 11: `/api/chat` streaming on API Gateway REST

**User Story:** As a developer, I want the chat to arrive by streaming through API Gateway, so that I validate the pattern the real agent will use.

#### Acceptance Criteria

1. THE `POST /api/chat` method SHALL be configured with `responseTransferMode: STREAM` and the `AWS_PROXY` integration type.
2. THE integration SHALL invoke the Lambda with `InvokeWithResponseStream`, using an integration URI that ends in `/response-streaming-invocations`.
3. THE chat handler SHALL use `awslambda.streamifyResponse` and `HttpResponseStream.from` to send `statusCode` and headers (`Content-Type: text/event-stream`, `Cache-Control: no-cache`).
4. THE REST API SHALL be of regional type, because the streaming idle timeout is 5 minutes for regional endpoints and 30 seconds for edge-optimized ones.
5. THE integration timeout of `/api/chat` SHALL be set explicitly and the Lambda timeout SHALL cover the full request cycle.
6. IF the CDK L2 does not expose the transfer mode, THEN `ApiStack` SHALL use the L1 resource `CfnMethod` or a documented property override.
7. THE rest of the endpoints SHALL stay in `BUFFERED` mode.
8. THE design SHALL record the known limitations: no endpoint caching, no content encoding, no VTL response transformations and no request streaming.
9. IF streaming does not work in the chosen region after verification, THEN the fallback SHALL be activated: a Function URL in `RESPONSE_STREAM` mode for `/api/chat` only, and the change SHALL be documented in the design.

### Requirement 12: Minimal CDK infrastructure

**User Story:** As a developer, I want to deploy everything with CDK from Phase 0, so that the first post has a public URL.

#### Acceptance Criteria

1. THE `infra/` project SHALL define an `App` with the stacks `ApiStack` and `WebStack`.
2. THE `ApiStack` SHALL create a regional REST API with resources under `/api`, request validation, restricted CORS, stage throttling and access logs.
3. EACH Lambda SHALL be defined with `NodejsFunction`, `Runtime.NODEJS_22_X`, `Architecture.ARM_64` and bundling with local esbuild (devDependency), without Docker or container images.
4. EACH Lambda SHALL have its own role with least-privilege permissions and SHALL NOT have access to Bedrock or AgentCore in this phase.
5. THE `WebStack` SHALL create a private S3 bucket and a CloudFront distribution with OAC, and deploy the `web/` build.
6. THE CloudFront distribution SHALL route `/api/*` to the REST API without caching and forwarding the required headers, so that the front end and the API share an origin.
7. ALL resources SHALL carry the tags `Project` and `Phase`.
8. EACH stack SHALL expose `CfnOutput` values for the site URL, the API URL and the relevant ARNs.
9. THE configuration (region, project name, phase, allowed origins) SHALL come from context in `cdk.json` or from variables.
10. THE bucket SHALL block public access and use encryption at rest.
11. `cdk synth` and the CDK tests SHALL pass before running `cdk deploy`.
12. THE site SHALL be served over HTTPS only.

### Requirement 13: Basic security

**User Story:** As the project owner, I want security limits from the start, so that I do not fix structural flaws later.

#### Acceptance Criteria

1. CORS SHALL allow only the configured origins (the CloudFront domain and `http://localhost:5173` for development).
2. THE front end SHALL NOT call AgentCore or Bedrock directly.
3. THE API SHALL limit the body size and the `code` field (maximum 20,000 characters).
4. ERRORS SHALL return generic messages without traces or internal details.
5. THE repository SHALL NOT contain secrets or credentials.
6. THE Phase 0 API is public and unauthenticated; THE design SHALL state this limitation and that the Cognito authorizer arrives in Phase 5.

### Requirement 14: Accessibility

**User Story:** As a student who uses a keyboard or a screen reader, I want to use the application without a mouse.

#### Acceptance Criteria

1. ALL controls (buttons, exercise selector, hints, chat input) SHALL be keyboard operable and show a visible focus indicator.
2. `TutorChat` SHALL announce new messages through an `aria-live="polite"` region.
3. THE Monaco editor SHALL let the user leave the field with the keyboard (for example `Esc` followed by `Tab`) and THE interface SHALL document that shortcut.
4. TEXT contrast SHALL meet at least 4.5:1 for normal text.
5. THE main regions SHALL use semantic elements and labels (`main`, `section` with `aria-label`).
6. Full WCAG validation requires manual testing with assistive technologies and expert review; this phase covers the basic checks above.

### Requirement 15: Quality and tests

**User Story:** As a developer, I want automated tests from the start, so that I can refactor with confidence.

#### Acceptance Criteria

1. ALL TypeScript packages SHALL compile with `strict: true` and no errors.
2. ESLint SHALL run without errors in `shared/`, `web/`, `api/` and `infra/`.
3. THE `web/` tests (Vitest + React Testing Library) SHALL cover: the API client, the SSE parser, the state of the run and hint buttons, and the results panel.
4. THE `api/` tests (Vitest) SHALL verify the contract of each handler with the `shared/` schemas and the absence of `solution` in every response.
5. THE `infra/` tests SHALL verify with assertions: Node.js 22.x runtime, arm64 architecture, `ResponseTransferMode: STREAM` on `/api/chat`, tags, private bucket, the `/api/*` CloudFront behavior and the absence of Bedrock permissions.
6. THE manual E2E test SHALL cover: open the module, chat, ask for the three hints, run and complete an exercise.

### Requirement 16: Documentation and post

**User Story:** As the author of the series, I want the documentation and the Post 1 draft at phase close, so that I can publish without extra work.

#### Acceptance Criteria

1. THE file `docs/posts/post-01-spec-driven.md` SHALL contain a draft about how to plan an agent project with Kiro (spec-driven).
2. THE draft SHALL include screenshots or descriptions of the front end, the demo URL and the decisions made.
3. THE README SHALL document a Phase 0 cost estimate (CloudFront, S3, API Gateway, Lambda).
4. THE spec SHALL record the status of open decisions 2, 4 and 4b of `stacky.md` (styling, streaming, one Lambda per responsibility).
