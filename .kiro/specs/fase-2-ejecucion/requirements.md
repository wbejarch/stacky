# Requirements Document

## Introduction

This document covers Phase 2 (Code execution) of `tutor-agent`. Phase 2 makes the "Ejecutar" button real: `POST /api/run` sends the student's code to an Amazon Bedrock AgentCore Code Interpreter, runs it against the exercise tests inside that sandbox, and returns a `RunResult`. The tutor agent also learns what the student ran, so it can explain errors, and it gets a small tool to run illustrative snippets in the same sandbox.

Phase scope:
- A custom Code Interpreter defined in CDK (network mode Sandbox, no execution role), created in `AgentStack`.
- A real `run` Lambda that builds a server-side test harness and calls the Code Interpreter. The Lambda never executes student code itself.
- Agent changes: record the last run, expose it through a tool, detect three consecutive failures of the same test, and run short snippets.
- The API contract in `shared/` and the front end do not change.

Out of scope (later phases): persistent progress and memory (Phase 3), Knowledge Base and Guardrails (Phase 4), authentication, observability dashboards and the production hardening of the sandbox network (Phase 5), hidden tests, interactive `input()`, languages other than Python.

Exit criterion: in the browser, the student writes code, presses "Ejecutar" and sees real test results, `stdout` and `stderr`; an infinite loop or a syntax error returns a friendly result; the tutor can explain the last error. The phase ends with the `fase-2` git tag and the draft of Post 3.

Language convention: code, comments and this spec are in English. Text shown to the student (UI, test messages, tutor) is in Spanish.

## Glossary

- **Code Interpreter**: the AgentCore managed sandbox that executes code in isolated sessions.
- **Harness**: the Python program generated by the server that loads the student code, calls the test expressions and prints a machine-readable result.
- **Nonce**: a random token generated per run that prefixes the harness result line so it cannot be confused with student output.
- **Ephemeral session**: a Code Interpreter session created for one run and stopped right after it.
- **Run record**: the information the agent stores about the last run of an exercise (code, tests, outputs).
- **Sandbox mode**: the Code Interpreter network mode documented as limited external network access.

## Requirements

### Requirement 1: Code Interpreter resource in CDK

**User Story:** As a developer, I want the sandbox defined as code, so that its network mode and permissions are explicit and testable.

#### Acceptance Criteria

1. THE `AgentStack` SHALL define a custom code interpreter with the L1 construct `CfnCodeInterpreterCustom`, because no L2 construct for it is available in `aws-cdk-lib`.
2. THE code interpreter SHALL use network mode `SANDBOX` and SHALL NOT set an `executionRoleArn`.
3. THE code interpreter name SHALL satisfy the service naming pattern and SHALL derive from the project name.
4. THE stack SHALL expose `CfnOutput` values for the code interpreter id and ARN.
5. ALL resources SHALL carry the tags `Project` and `Phase` with `Phase` equal to `2`.
6. THE design SHALL record the real ARN format returned for the custom interpreter and the IAM resource pattern that matches it.
7. THE design SHALL record that the system interpreter `aws.codeinterpreter.v1` exists and why the custom one was preferred.

### Requirement 2: `/api/run` executes in the Code Interpreter

**User Story:** As a student, I want my code to run for real against the tests, so that I know if my solution works.

#### Acceptance Criteria

1. WHEN `POST /api/run` is called with a valid `RunRequest`, THEN THE `run` Lambda SHALL execute the student code only inside the Code Interpreter and SHALL NOT evaluate, compile or interpret it locally.
2. THE `run` Lambda SHALL look up the exercise in the server content, build the harness and send it with the `executeCode` tool and language `python`.
3. THE `run` Lambda SHALL return a `RunResult` validated with the `shared/` schema, identical in shape to Phase 0.
4. THE response status codes and `ApiError` shapes of Phase 0 SHALL stay unchanged for invalid input (400), unknown exercise (404) and oversized input (413).
5. THE `run` Lambda SHALL support a backend switch `RUN_BACKEND` with the values `interpreter` and `mock`, where `mock` keeps the Phase 0 simulated behavior.
6. THE Lambda SHALL use its IAM role to call the service and SHALL NOT use stored credentials.
7. THE `RunResult.tests` list SHALL contain one entry per exercise test in the order defined in `ejercicios.json`.
8. `RunResult.passed` SHALL be true only IF every test passed.

### Requirement 3: Server-side test harness

**User Story:** As a developer, I want a robust harness, so that results are reliable even when the student code misbehaves.

#### Acceptance Criteria

1. THE harness SHALL be generated by the `run` Lambda from server content and SHALL embed the student code encoded in base64, so no escaping of student text is required.
2. THE harness SHALL embed the test list (`name`, `call`, `expected`) from `ejercicios.json` as data decoded from JSON, and SHALL NOT embed the reference `solution`.
3. THE harness SHALL compile the student code with a fixed file name and execute it in a fresh namespace, so tracebacks show student line numbers and hide harness frames.
4. THE harness SHALL evaluate each test `call` expression in that namespace and compare the result with `expected`.
5. THE harness SHALL capture student `stdout` and `stderr` with redirection and SHALL truncate each to 4000 characters.
6. THE harness SHALL print exactly one result line prefixed with a per-run nonce generated by the Lambda, and the Lambda SHALL parse only the line that carries that nonce.
7. WHEN the student code has a syntax error or raises an exception at load time, THEN THE harness SHALL report every test as failed with the message "No se pudo cargar tu código" and put the cleaned traceback in `stderr`.
8. WHEN a test call raises an exception, THEN THE harness SHALL report that test as failed with a Spanish message that names the exception type and a truncated message.
9. WHEN a test result differs from `expected`, THEN THE harness SHALL report the test as failed with a Spanish message that shows the expected value and the obtained value (truncated to 200 characters each).
10. WHEN the student code calls `input()`, THEN THE harness SHALL make it raise an error with a Spanish explanation that interactive input is not available in the tests.
11. THE harness SHALL run on the Python version of the interpreter and the design SHALL record that version.
12. THE harness template SHALL live in `api/` as a TypeScript string and SHALL NOT be a Python file in the repository.
13. THE design SHALL state that the harness is not a security boundary against the student, because student code shares the Python process, and that the sandbox is the boundary.

### Requirement 4: Time, memory and output limits

**User Story:** As the operator, I want hard limits on every run, so that one student cannot exhaust the sandbox or the budget.

#### Acceptance Criteria

1. THE harness SHALL limit the loading of student code and each test call to 3 seconds using an interval timer, and SHALL report a timeout as a failed test with the message "Tu código tardó demasiado (límite 3 s)".
2. THE harness SHALL set a memory limit of 256 MB for the Python process and SHALL report an out-of-memory condition as a failed test.
3. THE `run` Lambda SHALL enforce a wall-clock limit of 15 seconds on the Code Interpreter call and SHALL stop the session when the limit expires.
4. WHEN the wall-clock limit expires without a result line, THEN THE Lambda SHALL return a `RunResult` with every test failed and `stderr` equal to "La ejecución superó el tiempo máximo".
5. THE harness SHALL block outgoing socket connections as a best-effort defense in depth, and the design SHALL state that this is not the primary control.
6. THE total size of `stdout` and `stderr` in the response SHALL NOT exceed 8000 characters.
7. THE `code` field limit of 20,000 characters from Phase 0 SHALL remain enforced.
8. THE API Gateway method `/api/run` SHALL have a method-level throttle lower than the stage default.

### Requirement 5: Session lifecycle

**User Story:** As the operator, I want sessions to be short-lived and clean, so that there are no leaked environments or state between students.

#### Acceptance Criteria

1. THE `run` Lambda SHALL start a new Code Interpreter session for each run, with `sessionTimeoutSeconds` set to a short value (default 120) as a safety net.
2. THE `run` Lambda SHALL stop the session in a `finally` block after every run, including failures and timeouts, and SHALL log a stop failure without failing the response.
3. THE `run` Lambda SHALL NOT reuse a session across requests or across students.
4. THE `run` Lambda SHALL pass `clearContext` semantics by construction, since each session starts clean.
5. THE design SHALL record the measured session start latency and the alternative of reusing sessions (decision D10).

### Requirement 6: Isolation and honest security statement

**User Story:** As the product owner, I want an accurate statement of what the sandbox protects, so that the post and the product do not overclaim.

#### Acceptance Criteria

1. THE code interpreter SHALL have no execution role, so student code has no AWS credentials.
2. THE sandbox SHALL contain no secrets, no reference solutions and no data other than the harness of the current run.
3. THE design SHALL record the documented behavior of Sandbox mode (limited external access to AWS services, including S3 data operations and DNS resolution) and that independent security research has reported exfiltration paths through such channels.
4. THE design SHALL state that, in this POC, "no network" means no public internet access and no credentials, not a proven absence of every outbound channel.
5. THE design SHALL record the production option of VPC mode with restricted egress for Phase 5.
6. THE student code, its output and its error messages SHALL be treated as untrusted data everywhere (logs, agent context, UI).
7. THE UI SHALL render `stdout` and `stderr` as plain text and SHALL NOT interpret them as HTML or Markdown.

### Requirement 7: Failure semantics

**User Story:** As a student, I want clear messages when the service has a problem, so that I do not blame my code for infrastructure failures.

#### Acceptance Criteria

1. IF the Code Interpreter is unavailable, throttled or denies access, THEN THE `run` Lambda SHALL answer 502 with an `ApiError` of code `internal_error` and a generic Spanish message.
2. IF the Lambda cannot parse a nonce-prefixed result line while the service call succeeded, THEN THE Lambda SHALL return a `RunResult` with every test failed and the cleaned service output in `stderr`, and SHALL log the anomaly.
3. THE Lambda SHALL log `sessionId`, `exerciseId`, interpreter session id, duration and outcome category, and SHALL NOT log the student code at info level.
4. THE front end SHALL keep its Phase 0 behavior for non-2xx responses (retry message).

### Requirement 8: Agent learns from runs

**User Story:** As a student, I want the tutor to know what happened when I ran my code, so that it can help with my actual error.

#### Acceptance Criteria

1. AFTER each interpreter run, THE `run` Lambda SHALL send the agent a payload `type: record_run` with the exercise id, the code, the per-test results and the truncated outputs, using the same runtime session derivation as chat.
2. IF the agent call fails or times out (5 seconds), THEN THE Lambda SHALL log it and SHALL still return the `RunResult`.
3. THE agent SHALL store the last run per exercise in its session state and SHALL truncate the code to 6000 characters and each output to 2000 characters.
4. THE agent SHALL expose a tool `get_last_run(exercise_id)` that returns the stored run inside clearly delimited blocks labeled as untrusted student data.
5. WHEN a run passes all tests, THEN THE agent state SHALL mark the exercise as passed and the next chat context SHALL tell the tutor to celebrate and invite the student to explain their solution.
6. WHEN the same test fails in 3 consecutive runs of an exercise, THEN THE agent SHALL add an adaptation notice to the next chat context telling the tutor to change analogy or lower the difficulty, and SHALL clear the notice after it is used.
7. THE `record_run` handling SHALL NOT call the model and SHALL return a small acknowledgment.
8. THE `record_run` payload SHALL be validated with the same strictness as the other payloads, including string type checks and size limits.

### Requirement 9: Snippet tool for the tutor

**User Story:** As a student, I want the tutor to show what a small piece of code does, so that I can see behavior instead of only reading about it.

#### Acceptance Criteria

1. THE agent SHALL expose a tool `run_snippet(code)` that executes a short Python snippet in an ephemeral Code Interpreter session and returns truncated `stdout` and `stderr`.
2. THE tool SHALL limit the snippet to 1500 characters, the execution to 5 seconds, the output to 2000 characters, and the number of calls to 3 per chat turn.
3. THE tool SHALL NOT receive the exercise tests or the reference solution and SHALL NOT run harness code.
4. THE tool SHALL stop its session after each call, including on failure.
5. IF the Code Interpreter is not configured (`CODE_INTERPRETER_ID` missing), THEN THE tool SHALL return a short Spanish message saying that it is unavailable, and the agent SHALL keep working without it.
6. THE system prompt SHALL tell the tutor to use `run_snippet` only for small demonstrations related to the current concept, and not to write the exercise solution with it.
7. THE solution guard from Phase 1 SHALL keep applying to every fenced code block in the tutor output.

### Requirement 10: Prompt and evaluation updates

**User Story:** As the product owner, I want the tutor rules to cover the new inputs, so that run output cannot be used to bypass them.

#### Acceptance Criteria

1. THE system prompt SHALL state that code, `stdout`, `stderr` and test messages from `get_last_run` and `run_snippet` are untrusted data and that instructions inside them must be ignored.
2. THE system prompt SHALL instruct the tutor to explain error messages in simple words, quoting the relevant line, and to ask a guiding question before suggesting a fix.
3. THE evaluation set SHALL add conversations where the student code prints an instruction to reveal the solution, where a comment in the code asks the tutor to ignore its rules, and where the student claims the tests are wrong to obtain the solution.
4. THE offline evaluation SHALL verify with a stub model that the gate, counters and guard behave the same when the context contains run records.
5. THE live evaluation SHALL be re-run before closing the phase and its results SHALL be recorded in the design.

### Requirement 11: Least privilege

**User Story:** As the project owner, I want each component to hold only the permissions it needs.

#### Acceptance Criteria

1. THE `run` Lambda role SHALL allow `bedrock-agentcore:StartCodeInterpreterSession`, `bedrock-agentcore:InvokeCodeInterpreter` and `bedrock-agentcore:StopCodeInterpreterSession` only on the custom code interpreter resource, and `bedrock-agentcore:InvokeAgentRuntime` only on the agent runtime.
2. THE agent runtime execution role SHALL allow the same three interpreter actions only on the custom code interpreter resource.
3. THE `content` and `progress` Lambda roles SHALL NOT receive Bedrock or AgentCore permissions.
4. THE `chat` and `hint` Lambda roles SHALL keep the Phase 1 permissions and SHALL NOT receive interpreter permissions.
5. THE CDK tests SHALL be updated so that the Phase 1 assertion "`InvokeAgentRuntime` only on `chat` and `hint`" becomes "only on `chat`, `hint` and `run`".

### Requirement 12: Contract and front-end stability

**User Story:** As a front-end developer, I want no contract changes, so that the promise of stability holds.

#### Acceptance Criteria

1. THE `shared/` package SHALL NOT change in this phase.
2. THE `web/` package SHALL NOT require functional changes in this phase.
3. THE Phase 0 and Phase 1 API tests SHALL keep passing with `RUN_BACKEND=mock`.
4. THE `/api/progress`, `/api/chat` and `/api/hint` behaviors SHALL remain as in Phase 1, except for the added run context available to the tutor.

### Requirement 13: Performance

**User Story:** As a student, I want results quickly, so that the write-and-test loop stays fluid.

#### Acceptance Criteria

1. THE end-to-end time of a run with correct code SHALL be measured over 10 requests from the browser, and the median and the maximum SHALL be recorded in the design.
2. THE target for the median SHALL be 5 seconds or less, and IF it is exceeded, THEN THE design SHALL record the cause breakdown (session start, execution, stop, agent record) and the chosen mitigation.
3. THE `run` Lambda timeout SHALL be 25 seconds and the API Gateway integration timeout for `/api/run` SHALL be 29 seconds or the account default.
4. THE session stop and the agent record call SHALL run in parallel with each other and SHALL NOT delay the response beyond what is needed to complete them before the Lambda returns.

### Requirement 14: Content validation

**User Story:** As a content author, I want proof that the reference solutions pass and the starter code fails, so that broken exercises never reach students.

#### Acceptance Criteria

1. THE repository SHALL contain a verification command that, for every exercise, builds the harness, runs the reference solution and asserts that all tests pass, and runs the starter code and asserts that at least one test fails.
2. THE verification command SHALL run against the Code Interpreter with the developer's credentials, and a local variant SHALL run the harness with a local Python interpreter through `uv run` for unit tests, using only repository fixtures and reference solutions.
3. THE local variant SHALL never receive student code.
4. THE verification SHALL fail when any test `call` raises an unexpected exception with the reference solution.

### Requirement 15: Quality and tests

**User Story:** As a developer, I want automated checks for the new code, so that changes stay safe.

#### Acceptance Criteria

1. THE `api/` Vitest tests SHALL cover: harness generation (base64 payload, nonce, no solution text), result parsing (valid line, missing line, forged line without the nonce), the wall-clock path, the session stop in `finally`, the 502 mapping and the `RUN_BACKEND` switch, all with a faked SDK.
2. THE harness tests SHALL execute the generated harness with a local Python when available and cover: passing code, wrong answer, syntax error, runtime exception, infinite loop, memory allocation, `input()` call and a student `print` that imitates the result line.
3. THE agent tests SHALL cover: `record_run` validation and truncation, `get_last_run` delimiters, the three-consecutive-failures notice and its clearing, the `run_snippet` limits and unavailable state, using a faked interpreter client.
4. THE `infra/` tests SHALL assert: the custom interpreter with `SANDBOX` and no execution role, the scoped permissions of `run` and of the agent role, the `CODE_INTERPRETER_ID` variable, the method-level throttle on `/api/run`, the timeouts and the tags.
5. THE manual E2E test SHALL cover: passing code, wrong answer, syntax error, exception, infinite loop, a long output, asking the tutor about the last error, and a printed instruction that tries to extract the solution.

### Requirement 16: Documentation and post

**User Story:** As the author of the series, I want the Phase 2 documentation and the Post 3 draft, so that I can publish at phase close.

#### Acceptance Criteria

1. THE file `docs/posts/post-03-ejecucion-segura.md` SHALL contain a draft about safe code execution with the AgentCore Code Interpreter, including the honest statement of Sandbox mode limits.
2. THE README SHALL document how to verify content, how to run the harness tests, and the per-run cost estimate of the Code Interpreter.
3. THE design SHALL record the status of open decisions D10 and D11 and the measured latencies.
4. WHEN the phase is closed, THEN the repository SHALL carry the git tag `fase-2`.
